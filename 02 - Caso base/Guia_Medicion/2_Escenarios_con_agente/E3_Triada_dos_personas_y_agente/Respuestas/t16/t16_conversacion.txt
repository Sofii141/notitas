# Cómo funciona la primera versión

```python
def ordenar(notas: list[dict]) -> list[dict]:
    """Ver TAREAS.md, tarea t16."""
    return sorted(
        notas,
        key=lambda n: (
            -n["prioridad"],
            n["vence"] is None,
            n["vence"] or "",
        ),
    )
```

La idea es una sola línea de trabajo: **convertir cada nota en una tupla comparable** y dejar que `sorted` haga todo lo demás.

## 1. `sorted(...)` en lugar de `notas.sort(...)`

- `sorted` **crea una lista nueva** → cumple CA3 directamente, `notas` nunca se toca.
- `list.sort` ordenaría *in place* y mutaría la entrada. Por eso no se usa.
- Además `sorted` es **estable**: si dos elementos tienen exactamente la misma clave, mantienen su orden relativo original → cumple CA2 sin código extra.

## 2. La clave: una tupla de 3 posiciones

Python compara tuplas **posición por posición, de izquierda a derecha**, y solo pasa a la siguiente posición cuando hay empate. Ahí está todo el truco:

```python
(nivel, sin_fecha, fecha)
```

### Posición 1: `-n["prioridad"]` → prioridad más alta primero

`prioridad` vale 1 (baja), 2 (media), 3 (alta). `sorted` ordena **ascendente** por defecto, así que:

- Si usáramos `n["prioridad"]` saldría 1, 2, 3 → lo contrario de lo que pide CA1.
- Con `-prioridad` los valores son `-3, -2, -1`; el más negativo va primero → **3, 2, 1**, es decir alta → media → baja.

### Posición 2: `n["vence"] is None` → las sin fecha al final del grupo

Aquí no se ordena por la fecha todavía, sino por **"¿tiene fecha o no?"**:

| `vence` | `is None` | valor |
|---|---|---|
| `"2026-11-03"` | `False` | `0` |
| `None` | `True` | `1` |

`False` se comporta como `0` y `True` como `1`. Como la comparación es ascendente, `0` va antes que `1`:

- primero las que **sí** tienen fecha,
- al final las que tienen `None` → cumple "las que no tienen fecha van al final de su grupo".

Y como esta posición es la **segunda**, ese "al final" solo ocurre **dentro de la misma prioridad**: la posición 1 ya decidió el grupo. Una prioridad 3 sin fecha queda después de las 3 con fecha, pero antes de cualquier prioridad 2.

> Detalle importante: el `is None` está justamente para no comparar `None` contra un string. Si la tupla fuera `(prioridad, vence)`, Python lanzaría `TypeError: '<' not supported between instances of 'str' and 'NoneType'` en cuanto hubiera una nota sin fecha. Aquí `None` nunca llega a compararse como fecha.

### Posición 3: `n["vence"] or ""` → fecha más cercana primero

- Si hay fecha, se usa tal cual: `"2026-11-03"`.
- Si es `None`, `None or ""` devuelve `""` → un texto vacío, que **compara sin fallar** y quedaría antes que cualquier fecha real en orden alfabético… pero eso da igual, porque la posición 2 ya mandó esas notas al final del grupo. La posición 3 solo se evalúa entre notas que ya empataron en las dos anteriores (es decir, entre las que **sí** tienen fecha).
- Las fechas son `"AAAA-MM-DD"`: mismo ancho, año-mes-día. Comparar strings de ese formato da **el mismo resultado que comparar cronológicamente** (`"2026-11-03" < "2026-11-09"`), así que ascendente = vencimiento más cercano primero → cumple la segunda parte de CA1.

## 3. Recorriendo el ejemplo del test visible

```python
n = [
    {"id": "a", "prioridad": 1, "vence": None},
    {"id": "b", "prioridad": 3, "vence": "2026-11-09"},
    {"id": "c", "prioridad": 3, "vence": "2026-11-03"},
]
```

Claves calculadas:

| nota | `-prioridad` | `is None` | `or ""` | clave |
|---|---|---|---|---|
| a | -1 | True | `""` | `(-1, True, "")` |
| b | -3 | False | `"2026-11-09"` | `(-3, False, "2026-11-09")` |
| c | -3 | False | `"2026-11-03"` | `(-3, False, "2026-11-03")` |

Orden ascendente de claves:

1. `(-3, False, "2026-11-03")` → **c**
2. `(-3, False, "2026-11-09")` → **b** (empata en prioridad, fecha posterior)
3. `(-1, True, "")` → **a** (prioridad baja, además sin fecha)

Resultado: `["c", "b", "a"]` ✅ — exactamente lo que espera `test_t16.py`.

## 4. Dónde se cumple cada criterio

- **CA1** → posición 1 (prioridad), luego 2 (con fecha antes que sin fecha), luego 3 (fecha más cercana).
- **CA2** → no hay ninguna posición más: si dos notas empatan en las tres, `sorted` las deja en su orden de entrada porque es estable. Ojo: **no** se usa `id` como desempate, porque eso rompería la estabilidad.
- **CA3** → `sorted` devuelve una lista nueva y los dicts se leen, nunca se escriben.

## 5. Limitaciones / cosas que conviene tener en la cabeza

- Asume que `prioridad` y `vence` **siempre existen** en cada dict (si faltara una clave, sería `KeyError`).
- Asume fechas ISO bien formadas. Con `"03/11/2026"` la comparación de texto ya no coincidiría con el orden cronológico.
- `-n["prioridad"]` obliga a que la prioridad sea numérica; con strings (`"alta"`) fallaría.
- El `or ""` es un truco cómodo pero algo "impreciso": cualquier fecha falsy (solo `""` o `None` en la práctica) cae ahí. Es seguro **solo** porque la posición 2 garantiza que esos casos ya no llegan a compararse entre sí por fecha.
- Si en el futuro se quisiera un orden distinto para las notas sin fecha (p. ej. al principio), bastaría con invertir la posición 2 (`n["vence"] is not None`), sin tocar el resto.
